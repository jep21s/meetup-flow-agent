# meetup-flow-agent — архитектура агента

## 1. Задача агента

Telegram-группа о бесплатных IT-мероприятиях Санкт-Петербурга публикует сообщения о
митапах: пересылки из других каналов, ссылки на сайты регистрации. В сплошном потоке
тяжело отслеживать ближайшие события. Агент автоматизирует конвейер «сообщение →
календарь»:

- **Вход**: сообщение группы приходит на `POST /api/messages` (поставляет его
  внешний Telegram-прокси) и попадает во входящую очередь (inbox) с ключом
  идемпотентности.
- **Обработка**: сначала guardrails-проверка (промпт-инъекции, off-topic), затем
  агентный цикл извлечения структурированных данных с помощью инструментов
  (загрузка веб-страниц, поиск дублей, вопрос человеку), затем детерминированная
  пост-валидация жёсткого JSON-контракта и проверка на дубли по эмбеддингам.
- **Результат**: валидное мероприятие попадает в календарь (PostgreSQL + pgvector,
  `GET /api/events`); невалидное — статус REJECTED с причинами; повтор уже
  известного митапа — DUPLICATE со ссылкой на существующее событие. Прогресс
  обработки наблюдаем через `GET /api/flows/{id}` и SSE-стрим шагов.

Правила валидности: только Санкт-Петербург, бесплатно, обязателен офлайн-формат.

## 3. Агентный цикл (Reason → Act → Observe)

Оркестратор — собственный конечный автомат; на каждом цикле:

1. **Reason**: модель получает системный промпт, контекст (историю флоу, результаты
   инструментов) и возвращает либо `tool_calls`, либо финальный JSON.
2. **Act**: оркестратор исполняет затребованный инструмент (с учётом политики
   allow/ask/block) и возвращает результат как observation.
3. **Observe**: результат инструмента (или ошибка — тоже результат) добавляется в
   историю, цикл повторяется.

Решение «продолжать или завершить» принимает сама модель. Ограничители: лимит
итераций (база 8, авто-продление при прогрессе, хард-кап 16 — на капе агент
спрашивает человека), прогресс-детектор (нет изменений сигнатуры фактов два цикла
подряд — продления нет). Каждый шаг персистится в `flow_steps` (полная история,
включая рассуждения модели) и транслируется в SSE.

## 4. Модели и логика роутинга

| Задача | Модель | Почему |
|---|---|---|
| Guardrails: промпт-инъекции, манипуляции, off-topic | `glm-5.3` (Z.AI) | Задача безопасности: нужна максимальная надёжность классификации, вызовы редкие (один на сообщение) — можно дорогую модель |
| Агентный цикл, извлечение фактов, JSON-вердикт | `glm-5.3-flash` (Z.AI) | Массовые многошаговые циклы — важнее скорость и цена при достаточном качестве |
| Семантическая близость (дедупликация мероприятий) | Yandex `text-embeddings-v2-doc`, 768d | Специализированная embedding-модель; векторы хранятся в pgvector |

Принцип роутинга: **безопасность и сложные разовые проверки — сильная модель;
массовые агентские циклы — быстрая дешёвая; близость текстов — специализированная
embedding-модель.** Обе LLM доступны через единый OpenAI-compatible клиент.

## 5. Инструменты (function calling)

- `fetch_web_page(url)` — загрузка страницы регистрации (SSRF-защита, лимиты
  размера/таймаута/редиректов), HTML → текст; ошибки возвращаются модели как
  observation для самостоятельного решения.
- `search_duplicate(query, eventDate?, organizer?)` — векторный поиск похожих
  событий с фильтрами; агент сам решает, когда искать и когда хватит.
- `ask_human(question, contextSummary, options?)` — эскалация на человека:
  флоу ставится на паузу (снапшот состояния), уведомление через прокси, ответ
  возобновляет обработку.

## 6. Память

События хранятся в PostgreSQL с расширением pgvector: каждой записи сопоставлен
768-мерный эмбеддинг нормализованного представления (название + дата + место +
организатор), поиск ближайших соседей — HNSW-индекс (cosine). Гибридный поиск:
семантическая близость + WHERE-фильтры по дате (±3 дня) и организатору —
управляется агентом через инструмент `search_duplicate`. История самого флоу
(сообщения, рассуждения, результаты тулов) — в таблицах `flows` / `flow_steps`.

## 7. Надёжность и наблюдаемость

- Retry с экспоненциальным бэкоффом (1м→5м→15м→1ч→6ч, ≤6 попыток), circuit breaker
  по каждой внешней зависимости (LLM, БД, web).
- Идемпотентность: уникальный ключ сообщения в inbox; шаги флоу атомарны,
  снапшот состояния позволяет безопасно возобновлять после пауз и падений.
- Метрики Prometheus (`/internal/metrics`): статусы флоу, латентность и токены
  LLM-вызовов, вызовы инструментов, циклы ReAct; трейсинг OpenTelemetry → Jaeger
  (trace_id переживает паузы на ожидание человека).
- Логи — структурированный JSON с flowId/traceId; полные рассуждения модели
  пишутся только в БД, в лог-поток — краткие метаданные шагов.
